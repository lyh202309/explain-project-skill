# 讲解项目：先设计，后代码

## 为什么要有这个顺序

代码是方案的**结果**，不是讲解的起点。一上来读代码，再按文件顺序（Controller → Service → Mapper → Entity）或代码自上而下的顺序逐个念，听的人不知道「为什么要写这些」，任何一个类都记不住。

固定顺序：**先把问题讲清楚 → 可能需要补技术背景 → 再把方案讲清楚 → 最后才落到代码。**

## 第 0 步：先定讲法，交互式还是一次性输出

开讲之前先问用户这一句，因为它决定后面所有阶段怎么走：「你想一轮一轮来（我讲一段、你消化完确认了再讲下一段），还是我一次性把整套讲完？」

用户没明说时**默认按交互式走**——一次性倒一大堆内容，用户抓不住重点。

### 交互式（默认）

- **一轮只讲一个阶段**，讲完停下，等用户确认或追问，消化完了再进下一阶段。不要跨阶段输出。
- 每轮的收尾不是问一句「清楚了吗」就完事，而是用一句具体的、能验证他真懂了的话来确认，比如：
  - 讲完背景 + 功能清单 → 「这几条里你觉得哪条是核心？」，或者让他用自己的话说一遍其中一条。
  - 讲完候选方案 → 「A 和 B 的取舍你站哪边？」
  - 讲完选定方案 → 「现在能说出为什么不选 A 吗？」
  - 讲完实现链路 → 让他复述一遍链路，或者问某个环节的输入输出是什么。
- 某个阶段本身很长时（比如功能清单有十几条），**在阶段内部再拆轮次**，不要为了「一次讲完一个阶段」又堆成一大坨。
- 每一轮交互都要有明确的主题，主题要能让用户当场能消化。**「先输出一大段再问清楚了吗」不算交互式**，那只是给单向输出套了个问句的壳。

### 一次性输出

按下面的骨架完整写一遍。但**「技术预备」这一环不能省**：在开讲前花一次往返，把技术清单摆出来问用户哪些需要补（见 5.5），问完剩下的再一次性输出。用户明确说「都懂，直接讲」或者「全都讲」时，就照他说的办。

## 六段式骨架

按顺序走，每一段要回答的问题是固定的。

### 1. 背景

这个项目/模块在什么场景下存在，给谁用，解决谁的什么痛点，不做会怎样。

### 2. 功能清单

到底要实现哪些功能，逐条编号列出来。这是后面每一段的锚点——后面每讲一个方案、每一处代码，都要能指回这里的某一条。

### 3. 候选方案

针对第 2 段列出的功能，有哪几种主流做法。每种写清楚：做法是什么、好在哪、代价是什么、什么条件下才划算。用户没见过的方案点，先问一句懂不懂，懂的就跳过，不懂的就先补课。

### 4. 选定方案

最终采用哪一个，以及**为什么选它、为什么不选第 3 段里的其他几个**。选型理由要挂到功能清单的具体条目上（"因为要满足第 3 条，所以不能用 A 方案"），不要只说"A 更流行"。

### 5. 实现链路

这个方案从入口到落地，中间经过哪些环节、数据怎么流、每个环节负责什么。用编号步骤或链路图表达，**这一段还不看代码**。

### 5.5 技术预备：讲代码之前先补技术栈背景

第 5 段的链路里一定会冒出几个技术名词（例如LangChain4j 怎么做流式输出、SSE 是什么、Redis Stream 怎么消费、MyBatis 的 Mapper 接口为什么不用写实现类……）。用户很可能压根没见过这些技术在**当前项目这套技术栈**下是怎么写代码的。这时候**不要直接开始念项目代码**——他没有这个底子，念了也记不住，只会觉得「这个类是凭空冒出来的」。

**先盘点，再逐个问，再补课。**

1. **盘点**：把第 5 段链路里出现的、第 6 段要去读代码的每个技术点列成一份清单，逐条编号。列的是**技术点**，不是文件——写「例如LangChain4j 里 SSE 流式输出怎么写」，不要写「ChatServiceImpl.java」。
2. **逐个问**：把清单摆给用户，让他挑哪些是他已经会了的、哪些需要补。给明确的选项，不要含糊地问一句「这些你都懂吗」。用户说懂的跳过，说不懂的和拿不准的，都算需要补。
3. **补课**：对每个需要补的技术点，固定三步走，顺序不能调：
   - **通用做法**：先抛开本项目，讲这个技术在业界一般是怎么实现的——涉及哪几个角色、几个步骤、为什么非得这么绕。让他先明白「这东西是干什么用的」。
   - **最小例子**：给一个能跑通的极简示例，让他建立起类似于「我自己也能写一个」的底气。这个例子的代码**必须明确标注是通用示例、不是本项目代码**，也不要用项目里的类名、字段名、包名，免得和后面的项目代码搅在一起。
   - **项目实现**：有了上面两层再进第 6 段，对应到本项目的真实代码，重点讲「项目在这里比最小例子多了什么、为什么要多」。
4. **一次只补一个技术点**，讲完一个问一次再讲下一个。不要一口气把五个技术点的预备课全倒出来，那就又变成单向输出了。

### 6. 代码对应

把第 5 段的每个环节映射到具体文件、类、函数。用「环节 → `文件:行` → 这段代码在这里负责什么」的形式逐个对应。这一段才允许出现文件路径和大段代码。

**顺序不能调。第 6 段之前不要出现大段代码（5.5 里的最小例子除外，且必须标注是通用示例）。**

## 粒度按难度裁剪

不硬凑六个标题，但**顺序关系永远不变**（先问题、再功能、再方案、再补技术背景、后代码）。**5.5 技术预备在任何粒度上都不跳过**，哪怕只讲一个函数，也要先问一句这个技术点用户熟不熟。

| 讲解对象 | 怎么讲 |
| --- | --- |
| 第一次接触的完整项目 | 完整走六段式，并在第 2 段末尾把功能按需求域切成**模块清单**（见下一节） |
| 大项目里的某个模块 | 完整六段式。第 1 段背景要交代它在整体中的位置和上下游；第 2 段是这个模块自己的职责清单；第 3–4 段是模块内部的方案选型 |
| 一个文件 / 一个类 | 压缩成四步：它归属哪个模块、承担哪条功能 → 内部可以怎么写 → 这里为什么这么写 → 代码逐段对应；进入代码前先做 5.5 |
| 一个函数 / 十几行代码 | 不凑标题，讲清三件事即可：它要解决什么问题 → 有哪几种写法、要注意什么 → 这段代码逐句在干什么；用了什么用户可能没见过的技术点，先补一句 |
| 任何粒度上用户说了「详细讲」 | 按该粒度的上一档展开；函数级被要求详细讲时，就按「文件 / 类」的四步讲 |

## 第一次讲大项目：先切模块，别一口气讲完

第一次接触一个大项目时，不要试图一次把六段式讲完。

1. 走完第 1 段（背景）和第 2 段（功能清单）。
2. 在第 2 段末尾，把这些功能按**需求域**归成一份模块清单，逐条编号，每条一句话说明它负责哪几个功能点。
3. **在这里停下**，让用户挑先讲哪个模块。
4. 用户点某个模块后，对这个模块单独走一次完整六段式。

模块的切分依据是**需求 / 功能**，不是代码目录结构。目录结构是方案的结果，不能拿它当划分依据。

## 不要这样做

- 不要先翻一遍代码再倒推着讲——那是把顺序讲反了。
- 不要按文件顺序或代码自上而下逐行念。
- 不要在讲清楚「要解决什么问题」之前出现实现细节。
- 不要在完整六段式里跳过第 3 段：即使项目实际只有一种做法，也要说明为什么没选别的，否则听的人会以为「本来就只有这一种」。
- 不要不问用户懂不懂就直接讲某个技术的项目实现——默认他不懂，先问再补。
- 不要在 5.5 的最小例子里用本项目真实的类名、字段名、包名，也不要写完例子不标注它是通用示例。
- 不要把「输出一大段然后问一句清楚了吗」当成交互式；交互式是一轮一个窄主题，等用户真确认了再往下。
- 这个 skill 只管讲解顺序和讲法，不负责改代码。
